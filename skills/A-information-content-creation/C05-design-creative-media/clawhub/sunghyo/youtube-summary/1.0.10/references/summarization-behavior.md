# youtube-summary behavior

This file defines how summaries are produced across modes.

## Modes and summary source

- **Full mode** (`run_youtube2md.sh <url> full ...`)
  - Use first when a summarization provider is available (Codex ChatGPT login or `OPENAI_API_KEY`) and external API use is acceptable.
  - `youtube2md` generates Markdown summary output.
  - The runner passes `--model` only when the fifth argument or `YOUTUBE2MD_DEFAULT_MODEL` is set; otherwise upstream defaults (`gpt-5.6-luna`, overridable per provider via `CODEX_MODEL` / `OPENAI_MODEL`) apply.
  - The runner passes `--detail` only when `YOUTUBE2MD_DETAIL` is set (`concise` / `balanced` / `exhaustive`); the upstream default is `balanced`. Map user intent: "briefly / quick overview" -> `concise`, "very detailed / don't miss anything / near-transcript" -> `exhaustive`, otherwise leave unset.
  - Present the generated `.md` **verbatim** as the final answer — it is the finished, detailed summary. Do not condense it, drop chapters/bullets, or reflow it into a shorter template; only append the `Mode: full` line. Reformatting it into the compact simple-mode shape is the main cause of "the skill's summary is shorter than running youtube2md directly."
  - Do not re-summarize from raw transcript unless the user asks for a rewritten style.

- **Simple mode** (`run_youtube2md.sh <url> extract ...`, internally `--extract-only --extract-format timestamped-text --captions-only`)
  - Use for summary requests when no provider is available, content is sensitive, external API use is not acceptable, or full mode falls back.
  - `youtube2md` writes a timestamped transcript text file (`[MM:SS] line` per segment) directly; no post-processing step is needed.
  - Summarize using the timestamped `.txt` as the primary source; use its timestamps for chapter boundaries.
  - In user-facing output, call this `simple` mode, not `extract` mode.

- **Transcript mode** (`run_youtube2md.sh <url> extract ...`, internally `--extract-only`)
  - Use only when the user asks for transcript extraction, transcript-only output, raw transcript, captions, or machine-readable transcript JSON.
  - Default artifact is timestamped text; set `YOUTUBE2MD_EXTRACT_FORMAT=json` for the JSON transcript (includes metadata, `segments`, `transcriptSource`, `actualLanguage`, `autoGeneratedCaptions`) or `text` for plain text without timestamps.
  - Return transcript content or requested transcript artifact details, not a summary.
  - In user-facing output, call this `transcript` mode, not `extract` mode.

## youtube2md 1.1.0 behavior to trust

- Provider order with `--provider auto`: Codex SDK with ChatGPT login first, then the OpenAI Responses API when `OPENAI_API_KEY` is configured. Force one with `YOUTUBE2MD_PROVIDER=codex|openai`.
- Upstream default model is `gpt-5.6-luna` for both providers when no `--model` is passed.
- Long transcripts are chunked internally (boundaries snap to native chapter starts or speech pauses, with read-only overlap between chunks); trust the Markdown result when full mode succeeds.
- Both providers use structured output (Codex `outputSchema` / OpenAI strict `json_schema`); transient failures retry with exponential backoff.
- `--detail` (`concise` / `balanced` / `exhaustive`, default `balanced`) shifts how densely the transcript is mined for chapter bullets: roughly one description per ~360 / ~210 / ~120 transcript tokens respectively. Counts still scale with video length and content density at every level.
- Description counts are requested as a variable target band proportional to transcript volume, and summary paragraph / takeaway targets scale with video duration (a 3-hour video gets a multi-paragraph chronological overview). A response falling below the band's floor is re-requested once with an escalated prompt; the more detailed attempt is kept.
- Transcript retrieval tries captions first, then an alternate transcript parser, then Whisper STT (`whisper-1`) when `OPENAI_API_KEY` is available and `--captions-only` is not set.
- `--caption-lang` prefers an exact language-code match, then the same base language, then another available track.
- Full Markdown output adds a "Transcript source: OpenAI Whisper STT" notice when Whisper produced the transcript.
- Chapter display timestamps and their `?t=` links always agree; timestamps past one hour render as `[H:MM:SS]`.
- YouTube cookie env vars may improve captions/audio access for videos blocked to anonymous requests.

## Simple-mode summarization workflow

1. Load metadata (title, duration, publish date, URL/video id) from the JSON envelope (`YOUTUBE2MD_JSON=1`) or a JSON-format extract when available.
2. Load the timestamped transcript text from `.txt`.
3. Build a structured summary in this order:
   - `## Summary` (single dense paragraph)
   - `## Chapters` (chronological thematic sections; use transcript timestamps for boundaries)
   - `## Key Takeaways` (practical bullets)
4. Preserve factual values exactly when mentioned (prices, throughput, ping, wattage, dates).

## Summary density

> The density, chaptering, and takeaway heuristics below apply to **simple / transcript-derived** summaries that Claude authors. Full-mode output is passed through verbatim (see the Full mode note above) — do not shrink it to these counts. For longer videos, scale these baselines up rather than compressing to the minimum.

- Prefer a compact but substantial summary: enough detail to preserve the argument, setup, evidence, caveats, and conclusion without becoming a transcript rewrite.
- Include the speaker's conclusion or stance when it is clear from the transcript.
- If the transcript is mostly exploratory, preserve that uncertainty instead of forcing a stronger conclusion.

## Chaptering heuristics

- Prefer **3-7 chapters** for ~10-30 minute videos.
- Use concise section titles (topic/action based).
- Keep each chapter bullet list factual (2-4 bullets).
- Chapter bullets should explain what changed, what was tested, what evidence appeared, or what the viewer learned in that section.
- Avoid duplicate bullets across chapters.

## Key takeaways heuristics

- Prefer **6-10 takeaways**.
- Prioritize user-facing decisions:
  - when to use / when not to use
  - performance expectations and variability
  - cost and operational tradeoffs
- Include caveats and constraints (installation conditions, environment assumptions).
- Make takeaways decision-useful: what matters, why it matters, and any constraint that changes the decision.

## Mode disclosure

- End every user-facing video result with the actual mode used.
- Use `Mode: full` when youtube2md full mode produced the summary Markdown.
- Use `Mode: simple` when the summary was generated from extracted transcript text.
- Use `Mode: simple (fallback from full; no summarization provider available)` when full mode was requested but the runner switched to simple mode.
- Use `Mode: transcript` when the user requested transcript-only output.
- Do not use `Mode: extract` in user-facing output; `extract` is only the internal CLI/runner name.

## Language and uncertainty

- Keep summary language aligned with transcript/user language (Korean transcript -> Korean summary unless requested otherwise).
- For Korean videos or Korean user requests, write natural Korean with complete context, not overly compressed bullet-note Korean.
- Prefer matching caption tracks with `YOUTUBE2MD_CAPTION_LANG` when the user requests a specific language; check `actualLanguage` in JSON output to see which track was actually used.
- When transcript quality is noisy, auto-generated (`autoGeneratedCaptions: true`), or speech is unclear, summarize stable facts and mark uncertain details as uncertain.

## Quality guardrails

- Do not hallucinate specs, pricing, benchmarks, or policy claims.
- Preserve uncertainty from unclear speech or ambiguous transcript segments instead of smoothing it into confident claims.
- Keep the tone concise and useful; do not add analysis that is not grounded in the video.
